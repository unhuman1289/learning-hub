# Product strategy

## Product fit

Keep Learning Hub as a private notebook-based learning product. Its differentiator is a persistent record of what a person could do independently, what they still struggle with, and what to practise or review next. That proposition works across grammar, mathematical problem solving, code reading and professional reasoning. It is stronger than a pitch based on several subject menus or the ability to generate a lesson. The implementation already carries evidence and schedule, and no audit result establishes improved retention or full domain coverage. [Evidence schema](../../drizzle/0011_evidence.sql), [mastery and review](../../lib/learner-model/rules.ts#L165), [roadmap progression](../../lib/roadmap/progress.ts).

Start with adult Deutsch B1–B2 and a curated Grade 7 Maths notebook. Deutsch tests personalized feedback and retrieval. Maths tests deterministic correctness, different content structure and guardian workflow. Use success on novel prompts and delayed checks plus learner willingness to continue as the expansion criterion. Rust can next test source-rich technical tasks. Advanced cardiology can test source provenance and rubric agreement on synthetic cases under expert review. General knowledge can reuse reading and guided output while a reviewed curriculum is small.

| Curriculum and question bank | Framework and step validation, lesson version and stable local skill refs. No published course revisions or stable question reference across assignments. Cross-course comparability should use explicit mappings and reviewed anchors. |

**Boundary for sharing.** Public/course artifact fields can include published source, objective codes, content and rubric revisions, author/license and review history. Enrollment, goals written about a person, personal prompts, assignments, submissions, photos, grades, error patterns, mastery, review dates and tutor interactions stay in learner or authorized tenant scope. Shared exports should be generated from an allowlisted published-content projection and carry neither private IDs nor real attempts. Public-source inventory should expose only bounded public topic needs. Add positive and negative cross-tenant scope checks and an export-content test before introducing shared coursework.

## Comparison with ChatGPT Sites

Sites currently supports generating/hosting compatible web apps, D1/R2 storage, sharing and sign-in controls. Per-visitor plugin connections have workspace and privacy restrictions. The service organizes versions and links a compatible local project to deployed versions. Sites terms prohibit processing PHI and targeting children below 13 or the applicable age of digital consent. Sites authoring and hosting allowances are separate from verified runtime inference for the Hub. [Sites guide](https://learn.chatgpt.com/docs/sites), [data and connections](https://learn.chatgpt.com/docs/sites/data-and-connections), [version management](https://learn.chatgpt.com/docs/sites/managing-a-site).

| Dimension | Learning Hub | ChatGPT Sites |
|---|---|---|
| Speed to first experience | Already fast for a lesson fitting existing packages. New controls need source changes, tests and release. | Fastest for one-off visual/interaction prototypes from a prompt or existing code. Users still need to test data behavior. |
| Interactive exercises | Grading, support, retries, history and roadmap can reuse existing domain services. | A compatible app can implement custom web interactions, games and simulations. Grading rules, support/evidence capture and lifecycle still need app code. |
| AI integration | Qwen/LM Studio async plus separate scoped Knowledge MCP and a historical connector bridge. | AI-assisted building/editing and workspace-private per-viewer plugin calls are distinct capabilities. Official materials reviewed do not establish that any Site can run arbitrary learner-funded model inference. |
| Persistent knowledge and learning memory | Source versions and learner evidence are separate and tied to reviewed rules and schedules. | D1/R2 persist app data. Learning schema, delayed review, consent, backups and access checks still need design. Site sign-in by itself shares no ChatGPT memory. |
| Multi-user | Trusted household fit, independent users need dedicated tenant work. | Built-in site login/sharing makes membership quicker for eligible audiences. Course enrollment, assignment ownership, guardians and learner data isolation still require app authorization. |
| Portability | Git, JSON packages, SQL migrations, backup and restore scripts; original Sites identity retained. | A compatible Git project can follow the workflow. Hosting identity, connectors, authorization and storage need a cutover/recovery plan. Hub's standalone export and retained bridge illustrate the work. |
| Operations and scale | Owner operates Workers, database, backup and Mac. Full control of releases, history and evals. | Hosting, sharing and version management reduce setup. Runtime support, hosting entitlements, authoring usage and vendor constraints still apply. |
| Long-term use | Natural home for graded progress, restore, shared curricular IDs and product policy. | Supplementary prototyping environment for isolated adult/public synthetic tasks. A second production learner interface would split classrooms, identity and evidence. |

Potential delegated work includes reviewing a synthetic case layout, comparing two matching/listening UI designs, and prototyping a standalone static simulation. Bring back reviewed assets, lesson-package JSON or interaction code into the Hub's normal review. Use ChatGPT Work with the Knowledge-only MCP for staged public-source preparation, or use authoring offline with exported fixture contracts. Keep production publishing on Cloudflare and preserve `.openai/hosting.json` provenance. No Sites action or new publication is part of this audit. [Existing bridge](../../integrations/sites-bridge/README.md), [cutover documentation](../DEPLOYMENT.md), [package contracts](../../contracts).

## Strategic alternatives

Estimates are approximate engineer time for one developer familiar with the repo, plus learner/device/adjudication windows as noted. They compare decision scope, with cumulative commitments defined in the [roadmap](05_ROADMAP.md).

| Option | Expected benefit and effort | Migration / operations / risk | Long-term value, reversibility and dependency |
|---|---|---|---|
| **1. Incremental improvements** | Highest immediate benefit: reliable request and resume, defensible feedback, usable review on phones. ~3–5 engineer weeks across release/reliability, calibration and one pilot. | Low to medium migration, primarily finishing/rehearsing existing WIP and additive metrics. Low recurring spend plus Mac/support. Risk concentrates at old routes and phone regressions. | High reversibility with notebook flags and existing formats. Depends on release/restore evidence, QA and human calibration. Recommended now. |
| **2. Keep learning architecture, extend inference** | Better coverage when Mac is unavailable or a stronger model demonstrably improves a task. ~1 week for a synthetic comparison and 1–3 additional weeks for one approved adapter. | Low schema migration, moderate privacy/security and operational complexity. Provider cost varies (see cost model), with failure/circuit behavior and monitoring to maintain. | Reversible per task if contracts and DB stay stable. Depends on owner policy, measured accuracy/queue failure, approved data handling and independent spend decision. |
| **3. Refactor exercise and loop selectively** | Reduces schema failures and makes novel-context evidence, held-out review and domain-specific response options reusable. ~3–6 weeks if scoped to one new stimulus/evaluator plus versioned evidence links. | Moderate migration if touching package format, scoring or skill links. Integration V3 already covers persistence consolidation. Wrong equivalence, old grade changes or weakened support rules have high product impact. | Good value after two pilots expose the same bottleneck. Use additive version/metadata, dual-reader compatibility and replay tests. Avoid duplicate V3/L/G work. |
| **4. Redesign as a universal learning platform** | Maximum theoretical flexibility, uncertain learner value. Rough order 3–6 months for versioned curriculum, tenancy, execution, migration and quality baseline. | High migration and operational complexity, likely parallel releases, tenant/privacy burden, and grade/schedule consistency risk. Model capacity remains a separate operational expense. | Low reversibility after migration. Requires demonstrated demand and repeatable limitations across several cohorts and domains. Defer. |

## Decision inventory

| Action | Items |
|---|---|
| **KEEP** | Notebook UX and Vietnamese guidance, D1 evidence, versioned public-source knowledge, scoped job leases/apply receipts, Berlin scheduling, learner-owned work, guardian visibility, local Qwen with deterministic grading first. |
| **IMPROVE** | End-to-end job and grading telemetry, mobile/offline confirmation, source coverage, calibration and human disputes, delays/transfer evidence and documentation accuracy. |
| **REFACTOR** | Finish WIP consolidation of persisted packages and deduplicate evaluation dispatch as justified by fixtures. Add small stable objective and scenario references if reuse or measurement requires them. |
| **REMOVE** | Legacy v1 call paths, stale planner/assessor instructions and bridge capabilities only after caller inventory, data-preservation proof and separately authorized cutover. Keep historical readings accessible. |
| **BUILD** | A measured two-domain learning pilot, one portable reviewed pack and, when needed, one well-bounded evaluator or interaction. Build the tenant/access boundary before accepting independent families. |
| **DEFER** | Hosted SIWC plan usage, broad inference routing, a general exercise plugin framework, speech grading, executable arbitrary code, generic tutor chat, public multi-tenant launch and live clinical decision support. |
